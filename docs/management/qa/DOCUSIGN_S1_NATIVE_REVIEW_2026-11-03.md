## N1 — duplicate direct session command has no defined bearer-free response

**S1 locations:** §3 line56; §4 lines77–79 and88–97; §5 line115. These clauses must be read together:

- A live session ceremony URL is ephemeral and excluded from persistent outcomes (56,79,97).
- A direct `commandReply` confirmed session result requires `session:SessionLease` with its ceremony. A bearer-free `sessionReceipt` is allowed only for `replyKind=operationOutcome` from `readOperationOutcome`, and is explicitly forbidden in a direct-command case (88,93,97).
- Same authenticated account/kind/operationId plus identical input replays the durable outcome without repeating the provider call (115).

Concrete case: A explicitly issues session operationO1; provider issuance succeeds, then the direct response is lost or the process holding its ephemeral URL disappears. The persisted O1 outcome is confirmed. A duplicate direct `issueOwnSession(O1)` reaches the service with the identical binding. S1 currently requires durable-outcome replay, but its confirmed direct-reply case requires the unavailable bearer URL and forbids the persisted receipt. Reissuing a URL under O1 would repeat a provider effect; persisting/replaying a URL violates the proposed custody boundary; returning the receipt under `commandReply` violates the declared case table. This is not resolved by the already-correct rule that an outcome **read** returns a receipt. An explicit duplicate response is missing.

**Minimum docs correction:** define the exact safe response to a duplicate direct session command after confirmed issuance, including URL unavailable/expired/process-restart cases, and reconcile the universal idempotency sentence with the result table. For example, select one explicit bearer-free duplicate response that directs the client to `readOperationOutcome`, preserving the stored confirmed operation; or explicitly permit a separately typed receipt case for a duplicate direct response. The backend/shared-contract owner must choose one representation. Do not silently accept both, remint a URL, downgrade the persisted confirmed result to denial, or replay issuance. After a confirmed receipt resolves uncertainty, a new session still requires separate explicit intent and fresh policy/identity/recipient authorization; the receipt itself grants no launch/issuance permission.

Add future fixture design vectors for concurrent/same-key duplicate issuance, lost first response and process loss: exactly one provider issuance forO1, fixed safe duplicate shape, bearer-free outcome lookup, original immutable input/outcome retained, no automatic retry or ceremony, and separately authorized explicit replacement. These are proposed vectors, not tests run in this review.

**Native relevance:** accepted fake `Data/FakeExecutionRepositoryV01.swift:94–113,125–131` can replay/read its in-memory fake lease; `Domain/OperationOutcome.swift:100–116` requires that lease for a confirmed session; `Store/ExecutionSimulationStore.swift:197–224` can recover it into `sessionReady`. S1's live receipt intentionally cannot follow that path. The future service decoder/store must resolve receipt-only issuance without constructing a launchable lease. Accepted fake code remains unchanged.
