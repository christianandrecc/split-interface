# GM13G — artifact retrieval and native PDF fixture plan

November 6, 2026, America/New_York. **Docs-only proposal G1. No implementation, executable fixtures or passing runtime tests are delivered here.** The objective is a small, reviewable next local step toward GM06D, while retaining the React/Vite, SwiftUI and shared Supabase architecture. New real agreements still require the separately approved DocuSign integration. A PDF that opens, a matching hash, an in-app acknowledgement, or a simulated completion is not that integration.

Proposed review identifier: **`split.execution.artifact.fixture.proposal.v0.1`**, abbreviated **AF1** below. It is unimplemented and deliberately distinct from accepted native `split.execution.local.v0.1` and proposed future `split.execution.service.proposal.v0.1`. It does not modify either contract, S1/S2, or the accepted model. Do not add fields to an old strict DTO, alias AF1 to the service version, or reinterpret fixture provenance as `providerOriginal`.

## 2. Smallest staged next work, after separate assignments

1. **AF1 core/read fixture:** independent of canonical app navigation and accepted fakes, add only a strict artifact-read DTO/validator, injected byte repository, account-bound package store and deterministic tests. Preseed completion/read grants and immutable packages. No prepare/create/sign/session/void command, real provider, SQL or finalization worker. The first implementation handoff must name exact files/target; a possible isolated location is `ios/ExecutionArtifactFixture/`, not a modification of N1's wire meanings. A small language-neutral vector set lets web review the same request/metadata/bytes before an adapter is implemented.
2. **Native PDF inspection/share fixture:** only after core candidate independent acceptance and a separate bounded GM handoff, add a Debug-only read-only host with the iOS owner's chosen system PDF viewer and intercepted share presenter/materializer. It must not enter the production SPLIT account/store/navigation, change current partner-demo state, or issue signing commands. A build or PDF parse is not physical-device/VoiceOver/release evidence.
3. **Real GM06D/service integration:** remains blocked by reviewed actual service contract, D02/D04/D05 decisions, retained provider originals/certificate, genuine current authorization, shared guards and separate implementation/hosted authority. Neither fixture milestone completes this stage. No staging/project/account is provisioned by this plan.

The core is useful without actual provider credentials, hosted storage, legal retention periods, a production byte limit or a production PDF renderer. It cannot claim to validate those unresolved decisions. Later local code remains reversible development within the agreed scope; this document grants no implementation by itself.

## 3. Fixture-only inputs and provenance

Use GM13E's public A/B UUIDs, outsider C and revoked D, with an explicitly injected trusted fixture principal and account generation. This is no JWT/email/identity test. Do not map a native sample account or a supplied accountId/email into the trusted principal. The fake registry independently stores current grant/accessRevision and per-artifact read permission; each document **and certificate** is checked, even when package metadata was read earlier. A/B may read only explicitly seeded authorized package grants; membership or earlier signing is not a universal certificate-access rule. Production recipient/reader policy stays D05.

Two proposed package vectors: P1 has one prepared-document reference, one `executedSample` PDF and one separate `completionEvidenceSample` PDF; P2 has two ordered prepared-document references, two corresponding sample PDFs and one separate completion-evidence sample. P2 is a positive ordered-set control, not a decision that real SPLIT supports two documents. Every PDF's visible content/metadata and safe filename say **SPLIT SYNTHETIC FIXTURE — NOT AN EXECUTED AGREEMENT / NOT A CERTIFICATE** as appropriate; no real signatures, provider branding, seals or personal data. Prepared and executed samples are separately identified byte records, not regenerated from current sheet data on retrieval. Test terms/signers/source/encoding are synthetic and already frozen; this does not implement actual preparation.

Future fixture creation is separately assigned: this docs commit creates no binary or signable PDF. Review and freeze exact PDF bytes, digests, lengths, page counts and parser expectations before executing a viewer test. Use a deliberately unrenderable fixture with matching digest/length to prove that hashing alone cannot approve a PDF. File parsing is a display-safety check, not validation of an electronic signature, identity or legal execution.

AF1 needs its own frozen metadata derived from those new reviewed assets and fixture-specific encoding/renderer labels. Do not keep M1's 17-byte ASCII prepared digest, N2's text sample bytes, or N1's simulation media/headers while declaring the result to be PDF. The known attempt/config/environment references remain explicitly synthetic (the GM13E `demo` string makes no demo-service call); a wrong environment or source fixture cannot be normalized into the AF1 seed.

Proposed experiment budgets only: 1…1,048,576 bytes per artifact, at most three artifacts / 3,145,728 bytes per complete package, metadata at most 65,536 UTF-8 bytes, revisions/generations in the fixture range 1…1,000,000 / 0…1,000,000. Those bounds replace neither N1's 4KiB simulation nor a future production limit. No compression, streaming/range response, encrypted/password PDF, embedded attachment, active action or external link is accepted by the first fixture set. Negative fixtures stay small; no hostile resource-exhaustion test or malware certification. Production D04 must review parser/content/security budgets and the exact Int64/JSON number representation separately.

Manual clock and process-local lifetime only; no TTL, retention horizon, real bucket/path, user deletion, provider lookup or cleanup worker is selected. Fixture files may be discarded only inside the new test-owned directory; do not clean existing QA/Simulator/worktree data. Original legacy JSON/acknowledgement/history bytes remain untouched positive controls.

## 4. AF1 typed read proposal for cross-review

These are logical **injected calls**, not deployed paths, RPCs or a completed production wire schema. Every serialized response metadata root has exact `fixtureContractVersion = split.execution.artifact.fixture.proposal.v0.1`, `origin = syntheticFixture`, `fixtureSetId = af1-pdf-samples-v1`. The programmatic metadata/body pair is not a JSON body envelope. Unknown versions/origin/role/keys, null required values, unsafe numeric values, duplicate identifiers or implicit coercion fail closed. These literals cannot be changed to claim provider origin. Nested scalar/tuple field sets below refer to S1 section 3 for review vocabulary; new AF1-prefixed types and explicit decoding are required rather than casting existing strict DTOs. Expand the referenced nested field lists into identical Swift/TypeScript vectors before code acceptance.

Local transport tests may map a complete success to200/application/pdf and no-store; reject partial206, redirect, unexpected encoding/content type or error JSON. Header spelling/case normalization belongs in a later explicit adapter test; it is not accomplished by a value-object fake. Production C1/S1 binary HTTP headers, streaming, range, cache, same-origin proxy, signed URL and error mappings remain D04/version review, not inferred from AF1. No default public or signed URL fallback is permitted in the fixture. The fresh read context is not a transferable capability and cannot replace the server's current authorization.

Whole-package readiness requires simulated completion known, every frozen required party uniquely satisfied/signed and unambiguous, no missing/extra/unknown signer and zero unresolved recipients, current authorization for the explicitly selected execution, explicit manifest/byte permits, current exact manifest and every required artifact validated. `packageState=ready` alone is insufficient. A pending, declined, quarantined, unavailable or partially fetched package cannot publish ready/preview/share state. All downloaded data remains private staging until the entire set passes; any failure clears the staged whole package and older eligibility. Denial never falls back to N1 sample arrays, a cached generated legacy PDF or previously materialized certified copy. Explicit authorized history selection may read a superseded sample execution as AF-08 describes; that does not make it the current agreement or finalize a different execution.

Prepared digest, executed digest and certificate digest are preserved by role and explicit correspondence. Do not require that an executed digest equal a prepared digest, or treat digest inequality as evidence of execution. AF1's dataset intentionally has visibly different bytes, but that is not a production validity rule. A signed-PDF/certificate validation policy and actual provider document IDs/storage versions are still missing from the real service implementation.

## 5. Authorization, publication and materialization ordering

The fake repository checks current principal/account-generation and registry policy **before** reading metadata or retained bytes. After every manually suspended reply it rechecks authorization, the complete captured read/view/frozen/attempt tuple, the current manifest revision and that entry's current permission before publishing a body. Rechecking only the principal is insufficient when the manifest or view changed during transit. It resolves artifact identity from its own immutable manifest store; client input cannot select arbitrary storage objects. No successful response or state transition may be fabricated from a filename, status, current profile, untrusted event or matching email.

Client stamp captures `(accountId, workspaceGeneration, selectedExecutionId, selectionEpoch, projectionRevision, frozen, attempt, accessRevision, viewTag, accessObservationRevision, manifestId/revision when known)`. Recheck the exact captured stamp after projection, manifest, each byte response, digest/PDF inspection, file materialization and immediately before preview/share publication. A newer denial, access revision, account switch, selection/frozen/attempt change, removed permit or background invalidation makes every older success **and error** ineligible. Keep a local denial-observation revision as N3 does; merely cancelling a Task is insufficient. Do not let an old error clear a later valid package or an old success clear a later denial. A new explicit read of the latest authorized projection may recover eligibility; no automatic signing or request replay follows.

Use named, deterministic holds around `afterManifestAuthorizationBeforeReply`, `afterEntryAuthorizationBeforeReply`, `afterBytesBeforeValidationPublication`, `afterMaterializationBeforePresentation`, and `afterPresentationCheckBeforeHandoff`. Tests explicitly release promises/continuations, with no sleeps. Check the second artifact/certificate after the first succeeded: this is the native4f F1 regression shape. A newer current package positive must remain usable after stale work is suppressed.

For the later native host, prefer in-memory inspection before temporary-file creation. Materialize only already validated bytes in a new owner/account-generation/manifest-scoped test-owned directory with locally generated safe names, exclusive creation and atomic completion. Never use network documentId/title/Content-Disposition as a path, overwrite a retained original, append a cover/badge, or save a PDFDocument serialization as the only retained original. Before presenting a viewer or share sheet, re-read current permission through the fake repository, recheck the stamp and exact bytes; materialization is not an authorization receipt.

The iOS owner must review sandbox location, file protection/backup exclusion, path/symlink safety, cancellation/background/process-death cleanup and observable UI dismissal before code. Cleanup removes only its own ephemeral fixture copies, never retained source/legacy bytes or other sessions. Clear app eligibility on logout/revocation/background/selection change; on restart discard stale display/share eligibility and require fresh reads. A partial/temp file must never become a share item. Test write/rename/read failures and an unremovable temporary copy as explicit restricted failure/recovery states; do not claim successful deletion merely from hiding UI.

Share tests use an injected local presenter/consumer and inspect delivered bytes, names and item count; no Mail/AirDrop/external app delivery, real recipient or outbound action is authorized. A later system-share-sheet presentation check is separate from actual sending. Already handed-off files, screenshots or external copies cannot be recalled by app revocation/cleanup; production D05/privacy and the native handoff review must state that limit. Deterministic fixture barriers do not prove continuous or atomic real-world revocation between a final access read and an OS handoff. No automatic share on completion, refresh, foreground, callback or retry.
