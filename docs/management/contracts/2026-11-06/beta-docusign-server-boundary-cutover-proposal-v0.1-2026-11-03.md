## 2. Authoritative storage and identity proposal

Names are proposed logical relations in the existing non-exposed `split_private` boundary, not SQL definitions or approved migration names. Exposed wrappers stay narrow; privileged functions require explicit grants, fixed empty search paths and explicit authorization. Use caller-scoped invoker access where sufficient; any needed definer/worker privilege must be reviewed as a bypass of ordinary RLS, not treated as automatic authorization. Supabase documents [grants plus RLS](https://supabase.com/docs/guides/api/securing-your-api) and [function privilege/search-path controls](https://supabase.com/docs/guides/database/functions).

## 3. Proposed service values and DTO boundaries

This is a **review vocabulary**, not a generated client schema. Root JSON replies/commands carry reserved `contractVersion`; nested values have exactly the listed fields, with no simulation DTO headers. Nonempty IDs are opaque case-sensitive strings unless specified UUID; sheet/account IDs are UUIDs, revisions positive Int64 and generations nonnegative Int64. Proposed observedAt/expiresAt/retrievedAt serialization is RFC3339 UTC strings; timestamp values do not order projections and no session lifetime is selected. Required keys are nonnull. Optional keys are omitted, never null, except explicit `attempt:null` before a request. Unknown version, environment, policy, discriminant or security-relevant field fails closed. Version negotiation cannot grant permission. Production terms/signers/document-set encoding is identified by an approved encoding version; C1's ASCII fixture digest recipe is not used by assumption.

| --- | --- |
| `Digest` | `{algorithm:"sha256",hex:<64 lowercase hex>}` over the identified exact bytes/approved versioned manifest encoding. Digest is integrity/correlation, never identity or permission. |
| `OwnParty` | `{accountId:UUID,partyId,participantId}` from server canonical mapping. accountId is only the caller's. Full recipient/contact binding is private. |
| `ReviewBinding` | `{sheetId:UUID,proposalId,expectedSheetRevision,policyRevision,signerBindingRevision,termsEncodingVersion,reviewedTermsDigest,requiredSignerSetDigest,ownParty}`. | `FrozenBinding` | `{sheetId,proposalId,snapshotId,sourceSheetRevision,policyRevision,signerBindingRevision,termsEncodingVersion,termsVersion,templateVersion,rendererVersion,signedTermsDigest,requiredSignerSetDigest,documentSetDigest,documents:[PreparedDocument]}`. `PreparedDocument={documentId,order:Int64,preparedDigest:Digest,byteLength:Int64>0,mediaType:"application/pdf"}`. Lifecycle: `notRequested|createPending|signing|completed|declined|voided|expired`. Resolution: `known|uncertainCreate|uncertainSession|uncertainStatus|uncertainVoid|quarantined`. Evidence: `absent|assembling|ready|failed|quarantined`. Selection: `current|superseding|superseded`; supersession never rewrites an earlier completed lifecycle. Provider statuses outside the reviewed map remain unknown/quarantined rather than mapped to success. A returned session or individual signed fact cannot set lifecycle completed.

`permittedActions` is an array with unique values drawn only from requestExecution, issueOwnSession, readExecution, readOperationOutcome, readEvidenceManifest, downloadEvidenceArtifact and beginSupersession. It is a current account/view hint, not a transferable permission: each call is independently authorized and missing actions cannot be invented from lifecycle. Preparation eligibility belongs to the review reply before an execution exists.

Canonical provider completion requires server reconciliation of this exact account/environment/envelope/attempt, required-recipient set, current frozen binding and document correspondence. Finalization additionally requires all required parties uniquely satisfied, zero unresolved recipients, complete retained/validated original artifact manifest and current eligible policy/selection. Provider `completed` with evidence assembling is explicitly completion-confirmed/evidence-pending, with no finalized package eligibility. The UI never obtains a real verified badge from local simulation or legacy acknowledgements.

## 4. Actions, authentication, preconditions and effects

Proposed placement: a narrow Supabase Edge Function gateway for the typed actions below, delegating transaction work to reviewed Postgres wrappers/private functions and external work to a private adapter/outbox. Existing web/native Supabase authentication remains; no separate application/backend service is introduced. These are logical request bodies, **not deployed paths or RPC signatures**. A future endpoint names only allowlisted actions; public worker/Connect entry points have separate service authentication, never accept a collaborator's identity assertion, and cannot be reached by merely possessing a publishable key.

All user requests have `{contractVersion,action,input}`. Commands' input includes `operationId` and the exact command-specific binding; no trusted account ID outside server-issued ownParty. Server persists the authenticated initiating account separately. `workspaceGeneration` is a client publication guard, not server authority or a substitute for membership checks. Reauthorize before response/evidence publication; both clients must also capture/recheck account, generation, selected tuple and access/view revision after every await. New denial/access loss wins over a late earlier success, including errors, lease and artifact completion; cancellation alone does not establish this ordering.

Policy-sensitive collaboration needs a **separate reviewed versioned action boundary** for provider records: invite accept/decline, proposal accept/reject/counter, own registration update and chat each check authoritative policy and current frozen/attempt state first. ### Command outcomes and typed failures

`CommandOutcome={contractVersion,replyKind,operationId,commandKind,inputBinding,outcomeRevision,result,...casePayload}`. `replyKind` is exactly `commandReply` for a direct command response, or `operationOutcome` for readOperationOutcome. `commandKind` is prepareExecution/requestExecution/issueOwnSession/beginSupersession. `inputBinding` is the **exact immutable input** above, tied privately to initiating account: prepare has review and no execution yet; request has frozen execution but no guessed attempt; session has known full attempt; supersession has the then-known tuple. Confirmed result adds authoritative IDs without changing captured input. Its projection/lease must match every supplied precondition. A stale output never substitutes the latest tuple to make a comparison pass.

| result | Required case payload / forbidden members |
| --- | --- |
| `pending` | No projection/session/sessionReceipt/failure keys. The persisted operation exists; do not repeat the mutation. |
| `confirmed` | Prepare/request/supersession: `projection` only. Session with replyKind commandReply: `session:SessionLease` only. Session with replyKind operationOutcome: `sessionReceipt:{leaseId,executionId,frozen,attempt,ownParty,expiresAt,delivery:"notIncluded"}` only, with exact issued binding and no ceremony URL. This receipt confirms prior issuance, not present permission to launch or permission to mint/replay it. No failure or other result payload. |
| `denied` | `failure` only, same operation ID, no result body. A safe pre-dispatch refusal is distinct from an uncertain external call. Unauthorized lookup returns standalone generic denied, no stored input binding. |
| `unresolved` | `failure` only with uncertainOutcome, same operation ID and recovery readOperationOutcome. Last confirmed facts remain visible through readExecution; unknown is not notRequested/failure. |

Case-inappropriate keys are absent, never null; required members cannot be null. Denied/unresolved also forbid sessionReceipt. The replyKind/commandKind/result triple determines one exact payload case; reject a session URL in any outcome-read case, a receipt in a direct-command case or multiple payloads. Archived projection/receipt fields remain immutable for that outcomeRevision; current access is rechecked separately and denial cannot expose an archived bearer. These proposed reply distinctions intentionally differ from the in-memory simulation, which holds fake leases rather than a live bearer URL. Public HTTP mapping below is for future gateway review; existing PostgREST clients see their existing error conventions and cannot be assumed to decode it.

## 5. A/B idempotency, Connect and evidence reconciliation

Under one consistent lock order (sheet identity → policy → execution → attempt/operation), compare policy and authorization before accepting command intent. Same initiating account/kind/operationId and exact request digest replays the durable outcome, not the provider call. Different input is idempotencyConflict. A/B's independent keys still contend on one execution-level active-or-uncertain attempt constraint. Persist transaction ID scoped to exact provider account/environment before dispatch; configuration cannot change under that attempt. A dispatch claim is durable; a crash after claim is treated as possibly sent. No missing queue acknowledgement licenses another create.

DocuSign documents transaction-ID recovery and a **seven-day validity window**; this is not a permanent exactly-once guarantee. Lookup only within the stored sending account/environment; one matching envelope still requires recipient/document/snapshot validation. Multiple/conflicting matches quarantine. No match, timeout, lookup-window expiry, restored ledger or absent envelopeId does not prove noncreation; retain uncertainCreate and block A/B from another create until reviewed recovery. Provider error classification must prove a call was not accepted before allowing a fresh explicit attempt; ordinary network errors cannot. [Official transaction-ID guidance](https://www.docusign.com/blog/developers/common-api-tasks-use-transactionid-to-find-the-envelope-you-created).

Connect proposal uses an existing-architecture dedicated Edge Function admission seam and Postgres durable inbox; no new cloud queue is required by this design. Its future endpoint authenticates the **exact raw body** with configured HMAC-SHA256/base64 signatures before parsing business data, using a bounded body and constant-time comparison against allowed key versions. Do not trust caller-selected algorithm/key/account or reserialized JSON. Key rotation must preserve explicit allowed overlap; no header alone confers sender identity. HMAC is not freshness or agreement authorization. [Official raw-body HMAC guidance](https://www.docusign.com/blog/developers/manually-authenticating-hmac-signatures-docusign-connect-webhook-configurations).

After authentication, safely parse the reviewed Connect format; validate configured provider account/environment, subscription/configuration and known envelope/attempt. Known-envelope events may be durably admitted. Unknown-envelope events use a bounded restricted correlation quarantine with no document fetch/canonical update; only the request ledger plus authorized provider lookup can adopt them. Invalid authentication gets 4xx/no trusted inbox work. Authentic wrong-scope/malformed events receive a durable rejection/quarantine disposition before neutral acknowledgement; admission-storage failure gets 5xx so receipt is not falsely acknowledged. Exact response/rate/body limits await D07. Authenticate before recording payload as trusted; ordinary logs contain neither raw agreements nor secrets.

Acknowledge with200 only after durable receipt/disposition (including duplicate receipt); reconcile asynchronously. DocuSign recommends prompt acknowledgement and queued handling; this proposal follows that capability rather than doing PDF retrieval in the listener. [Connect implementation guidance](https://developers.docusign.com/platform/webhooks/connect/implement/), [asynchronous listener guidance](https://www.docusign.com/blog/developers/dsdev-webhook-listeners-part-2).

Dedupe first by configured scope + raw-body digest (and trusted message ID when documented for the chosen format); do not assume a globally unique event ID or signed timestamp. Semantic idempotency additionally uses normalized event/reconciliation keys and execution revision constraints: retries with changed envelope ordering/timestamps cannot repeat finalization/audit/artifact writes. Raw replay may be admitted/deduped, but arrival time never wins a lifecycle conflict. Worker validates exact envelope, recipients/roles and document correspondence against persisted private binding and reads authoritative provider state using the pinned sending configuration. A sent event after completed cannot regress; terminal contradictions quarantine while preserving prior facts. Authenticated events are triggers/evidence, never a replacement canonical document or instruction to run the legacy sign RPC.

UI return/Close/session callbacks are read-only navigation hints. Forged/replayed/wrong-account correlation yields denial or allowed local status read, never completed/declined/void/request/session issuance. DocuSign warns that return URLs can be spoofed/cancelled and assigns embedded-recipient authentication responsibility to the application. UI reads use SPLIT's projection and do not cause provider polling; worker reconciliation must obey current API/Connect rate budgets and coalesce notifications. [Recipient-view reference](https://developers.docusign.com/docs/esign-rest-api/reference/envelopes/envelopeviews/createrecipient/), [Connect polling guidance](https://developers.docusign.com/platform/webhooks/connect/).

Evidence worker retrieves each expected provider-executed PDF and the completion certificate as separately identified artifacts from the pinned account/envelope. Store the exact returned bytes as immutable originals with fresh byte digests, full length/type/correlation checks and approved D04 validation. Never expect the executed digest to equal the prepared digest; preserve both and explicit correspondence. A combined download may be a separately identified provider-returned representation if reviewed; it cannot replace required individual provenance silently. Do not regenerate signed originals from current app data or append a SPLIT badge/cover to the only retained original. [Official document retrieval](https://developers.docusign.com/docs/esign-rest-api/reference/envelopes/envelopedocuments/get/), [official SDK retrieval reference](https://docusign.github.io/docusign-esign-node-client/module-api_EnvelopesApi.html).

Finalize through a guarded dedicated transaction only after current policy/snapshot/selection/private recipient mapping, provider completion and retained complete artifact set all match. One immutable finalization record/audit per exact execution+manifest, never fabricated `SPLIT in-app acknowledgement` rows or provider calls impersonating collaborators. This proposal does not prescribe writing legacy status/verified_at or changing the protected historical document; provider finality is a distinct record/projection and any canonical-app integration needs its own review. Status/evidence retrieval can recover independently: storage failure leaves completion known/evidence failed or assembling, not finalized. Reauthorize artifact and certificate separately on every read. Private bucket/RLS is a proposed mechanism, not a configured resource; public URLs bypass private access and are unsuitable. [Supabase private bucket controls](https://supabase.com/docs/guides/storage/buckets/fundamentals).

E1 late completion after E2 supersession is retained against E1 and flagged; it cannot finalize E2, erase original evidence or be discarded as merely stale. Unknown void blocks replacement dispatch. Completed/finalized originals, historical acknowledgement JSON/signatures and signed bytes remain immutable. A later dispute/access change/security contradiction appends an operational finding/access restriction; it does not silently edit the old signed terms, pretend consent was revoked retroactively or rewrite history. Recovery decision for a possibly executed superseded agreement is an operator/legal gate, not an automated client action.

## 6. Legacy entry-point enforcement and installed-client behavior

Central proposed guard takes locked sheet identity, authoritative policy, route/action and execution state. A missing or unsupported policy denies eligibility; it never falls through to legacy. Put the guard in every private mutation implementation and defensive wrapper, before JSON normalization/replacement, registration capture, status/revision changes, sync, notification/outbox effects or provider dispatch. Locks/read-only validation may occur first. A denied command leaves no canonical/registration/response/audit/notification/outbox effect; a separate sanitized security observation is permitted outside the agreement's history. Guard existing row and attempted creation separately: absent-row advisory locking must classify new records before any payload can select legacy.

| Legacy surface | ProviderRequired / unknown policy behavior before effect | Genuine classified legacy positive control |
| --- | --- | --- |
| `load_my_split_sheets` and any legacy single/read/export path | Exclude provider/unknown rows **before normalize_pending_split_signatures and visible_document**, not after. Do not return a legacy-shaped stub/status/verifiedAt. For a single-ID route return fixed legacyRouteUnavailable without body. | Preserve existing ownership/privacy projection, unknown historical fields and exact original signed records. Unchanged mixed collection returns all allowed legacy rows, even if provider rows exist. |
| Public and private participant update, **all** invite/approval/counter/sign/chat actions | Reject entire old route for providerRequired/unknown, even for local_chat; no legacy status recomputation or registration side effect. New reviewed collaboration boundary is required. | Existing action-specific author/revision/consensus/own-sign checks and allowed chat continue. Final legacy records stay immutable. |
| Public/private upsert: draft, send, update, attempted contract_delivery; absent-row creation | Existing provider/unknown always denied before replacement. After cutover new creates select server provider policy and old upsert fails before insert/collaborators/outbox; body omission/spoofed legacy policy cannot grandfather a new sheet. | Previously classified eligible legacy drafts continue approved behavior under current ownership/revision/final guards. Decision whether unfinished legacy may continue signing is D01; until settled, gate new legacy execution separately rather than mislabel it provider. |
| Draft delete / cleanup / internal writes | Provider snapshot/attempt/finalization/evidence existence blocks cascading deletion. Missing policy is not proof of a safe legacy draft. | Verified unsent unsigned classified legacy draft deletion works; absence/retry semantics maintained. Never delete evidence to satisfy a legacy precondition. |
| Direct SELECT column grants: split_sheets, collaborators, proposal/response/audit/delivery; views, Realtime, notifications | Filter provider/unknown rows at authoritative row policy/security-invoker projection; grant changes alone cannot distinguish rows. **Mixed collection proposal:** keep legacy RPC return shape unchanged and row-filter it as above. A new provider-capable `listAgreements` read returns a versioned discriminated collection: `{items:[{kind:"legacyInApp",sheetId,legacyDocument}|{kind:"providerRequired",sheetId,executionSummary}|{kind:"unsupported",sheetId,reasonCode}],cursor?}`. Each item gets its own authorization/privacy check; only authorized owners may see an unsupported placeholder. Missing policy never exposes provider data. `executionSummary` is a typed minimal `{executionId?,lifecycle?,evidence?,selection?,viewTag}` with state fields absent before preparation, not a legacy certified document. A full-read dispatch by discriminant is mandatory; unsupported item cannot enter a legacy parser/export.

An unchanged old client may omit provider agreements entirely, display a generic save/action error, retain an old cached draft, or generate an offline historical/local file. **No upgrade screen or global cache erasure is promised.** Client capabilities/version headers are UX negotiation, not security. Updated web/native owners must distinguish missing server access from a local draft, stop resend/offline consent queues, invalidate provider export/sign eligibility after denial, and label historical/local exports truthfully. Cached previously delivered originals cannot be recalled. Release communications/minimum supported installed-version policy need D01/D03; until approved readers/guards are verified together, no real provider-required records are accepted.
