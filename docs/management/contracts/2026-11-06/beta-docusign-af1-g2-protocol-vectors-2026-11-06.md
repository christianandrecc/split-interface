It has no `displayEligible`/`shareEligible` result, PDF parser, presentation API, file URL, FileManager/storage, SDK, network transport or canonical application dependency. No root `ios/Package.swift`, accepted `ExecutionSimulation`, SDK pin, app project/navigation/session or production runtime floor changes are implied. These paths and targets are proposals for GM's next explicit handoff, not files created here.

Later actual PDFKit inspection must separately establish `PDFDocument(data:)` success, reviewed expected nonzero pages, `isEncrypted == false` and `isLocked == false`, using approved valid, matching-digest-malformed and encrypted/locked fixtures. ### 4.2 Manifest and view versions

For each exact `(fixtureSetId,executionId,frozen,knownAttempt)`, manifestId is stable and each `(manifestId,manifestRevision)` is an immutable complete record. G2 seeds P1/r1, P1/r2 and P2/r1 only. P1/r2 retains the same original artifact IDs/body bytes/digests/order/roles and uses new retrievedAt/reconciliationId metadata; it is a separate approved immutable record, not an edit to r1. P1/r2 becomes current only with projectionRevision11, observedAt17:00:01Z and A/B viewTags updated as section5 defines. No response may itself create a manifest version. The stable ID/revision and caller view are trusted-registry selections before a read, not values learned as authority from the delivered manifest. Actual content replacement requires a different reviewed frozen/attempt/execution oracle, not a self-declared higher revision.

Client acceptance maintains a process-local high-water mark per authorized selected package binding and account context. Older projection/manifest revisions cannot replace a later observed one. Equal revision with differing decoded body is integrity conflict/quarantine, never last-arrival-wins. A same-binding unexpected new manifestId is integrity failure. Different stored entries/bytes under the same ID/revision are integrity failure, even if all response digests agree with each other. A higher approved manifest revision must coincide with a higher current projection revision and changed viewTag; invalidate prior in-flight package loads and require a new owned complete read, never mix old/new entries. Timestamp order is irrelevant. Do not claim to detect an unobserved server change.

The fake repository exposes current revision changes through fresh projection/manifest reads or an explicit current authorization/context invalidation notice. A held old reply does not become “latest” merely because delivered later. A fresh complete read with the approved newer view may recover from staleRead; integrity quarantine for an equal-conflicting record requires explicit reset to a newly selected trusted fixture world, not a silent retry of attacker data. On account/context replacement discard previous published bytes/diagnostics; oracle checks still apply to the new authorized reader.

## 7. Local ownership and deterministic publication order

Wire requestId/viewTag and an unchanged server tuple are **not** invocation owners. The store has a private process/store instance nonce, monotonic accountGeneration and selectionGeneration, monotonic loadSequence and independent accessObservationEpoch. `beginExplicitLoad()` always issues a new private `LoadOwner=(storeNonce,accountGeneration,selectionGeneration,loadSequence)` even if every server field is identical. It invalidates older owners, clears published integrity result and private staging, and starts projection→manifest→each byte→whole-set validation for only the newest owner. No automatic load/sign/share occurs on callback, foreground or recovery. Retire the store/reissue a new instance nonce before any local counter overflow; never wrap/reuse a token.

Every continuation, typed failure, thrown decode/hash/read error and stage-publication captures LoadOwner and the full read context when known. Before changing state it must still own the load and match account/selection/context/accessObservationEpoch. Stale work does nothing: no byte/error publication, no clearing newer eligibility, no high-water-mark/counter/denial-epoch advancement and no cleanup of another owner. Current-owner compare-and-publish and watermark mutations are serialized in one local store isolation domain; there is no suspension between the final owner/epoch check and state publication. A current owned failure restricts its own result and clears its own staging; an old failure delivered after a newer positive cannot become a new denial merely by arriving later. Same-context L1/L2 calls are therefore ordered by local owner, not diagnostic requestId or body revision.

Separately, a current-context authorization observer/invalidation notice is bound to an independent current observer generation and account/selection identity. A freshly accepted current denied result, revoked per-entry grant, removed permit or accepted newer access/context revision increments accessObservationEpoch and invalidates all current loads/results; an obsolete observer or obsolete load cannot emit that notice. This preserves newer-denial suppression after a load completed. ABA A→B→A or E1→E2→E1 still advances account/selection generations, so old tokens cannot revive. Notices are an explicit trusted fixture seam, not a production push-auth protocol. An unobserved remote permission change is not detectable by local token comparison alone.
